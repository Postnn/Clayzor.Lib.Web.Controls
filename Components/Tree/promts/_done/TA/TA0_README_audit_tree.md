# TA0 — Аудит ClayTree: находки и порядок исправлений

Серия TA (Tree Audit). Промты выполняются строго по порядку номеров: TA1 → TA7.
Каждый промт разбит на шаги; один шаг = один файл; файлы внутри промта пронумерованы
в порядке правки (сначала слой Entities, затем Controls).

## Сводка находок

| # | Серьёзность | Находка | Промт |
|---|---|---|---|
| 1 | **Критично (безопасность)** | SQL-инъекция через `ClayTreeOptions.OrderBy`: `BuildOrderBy` валидирует только имя колонки, хвост после имени (`DESC; DROP …`) и содержимое после `[Имя]` попадают в SQL без проверки | TA1 |
| 2 | **Критично (runtime)** | Дефолтный фильтр (`FilterDefaults`) генерирует `ExtraWhere` с параметрами `@p0…`, но сами параметры выбрасываются (`var (defWhere, _) = BuildDefaultWhere()`), в `ClayTreeData.BuildParams` они не попадают → SQL Server: «Must declare the scalar variable @p0» при первой же ленивой загрузке | TA2 |
| 3 | **Критично (потеря данных состояния)** | `ClaySqlTreeStateStore.BuildParamNames` использует `treeId.GetHashCode()` — в .NET хеш строк рандомизирован на каждый запуск процесса → сохранённое состояние не читается после рестарта приложения; `Math.Abs(int.MinValue)` кидает `OverflowException`; `ToString("X6")` даёт до 8 символов и после обрезки до 20 ключи anchor/sel могут совпасть | TA5 |
| 4 | **Высокая** | Компонент никогда не выполняет первоначальную загрузку: `OnInitializedAsync` не вызывает ни `LoadRootsAsync`, ни `ApplyFilterAsync`; forced-фильтр из URL распарсен в `_filterRoot`, но к данным не применяется | TA3 |
| 5 | **Высокая** | `ResolveDataSourceForNode` игнорирует пользовательский параметр `DataSource` (тестовый источник подменяется SQL-источником при включённой пагинации) и теряет `ExtraWhere` (страницы уровня грузятся без дефолтного фильтра) | TA4 |
| 6 | **Высокая** | `OnParametersSetAsync` сравнивает `RootId` оператором `!=` (сравнение ссылок для boxed-значений → ложные перезагрузки), не отслеживает `OrderBy`, и при пересоздании `_source` теряет `ExtraWhere` | TA3 |
| 7 | **Средняя** | ParentKey-режим: рекурсивные CTE (`BuildParentKeyFilterSql`, `LoadAncestorChainAsync`) без защиты от циклов в данных → ошибка 530 «max recursion»; флаг `[_hasmatchchildren]` вычислен неверно (узел-совпадение с совпавшими потомками не получает пометку) | TA1 |
| 8 | **Средняя** | `BuildTreeFromFlatNodes`: `Level` детей проставляется в произвольном порядке словаря → в ParentKey-режиме внуки получают неверный уровень (сломанные отступы); `_expanded` не синхронизируется с раскрытым фильтр-набором | TA6 |
| 9 | **Средняя** | Переполнение лимита фильтра: SQL берёт `TOP (@max + 1)`, дерево показывает max+1 совпадений, а сообщение утверждает «отображаются только max»; `MaxFilterRecords = 0` задокументирован как «без лимита», код молча ставит 100 | TA6 |
| 10 | **Средняя** | `EnsureChildrenLoadedAsync` не защищён от повторного входа (двойной клик → две параллельные загрузки); `catch (Exception)` в `ClaySqlTreeDataSource` глотает `OperationCanceledException` (отмена показывается как ошибка) | TA4 |
| 11 | **Низкая** | `MapRow`: `l as long? ?? (l is int li ? li : null)` — ключи `decimal`/`smallint` из БД превращаются в null → NestedSet ломается на не-int ключах | TA4 |
| 12 | **Низкая** | `ClayTreeNodeView.Dispose` делает fire-and-forget `JS.InvokeVoidAsync` без try/catch → необработанный `JSDisconnectedException` при закрытии circuit; `BuildFilterColumns()` вызывается в разметке на каждый рендер | TA7 |

## Порядок выполнения

1. **TA1** — безопасность и корректность SQL-билдера (Entities).
2. **TA2** — параметры `ExtraWhere` через все слои (Entities → Controls).
3. **TA3** — жизненный цикл: начальная загрузка, применение URL-фильтра, `OnParametersSetAsync`.
4. **TA4** — источники данных и ленивая загрузка.
5. **TA5** — стабильные ключи персистентного состояния.
6. **TA6** — режим фильтра: уровни, счётчик, лимит.
7. **TA7** — мелкие UI-правки.

После каждого промта: `dotnet build` без ошибок и предупреждений по затронутым файлам,
прогон существующих тестов дерева.
