# CTF2 — NestedSet без `LevelColumn`: вычислять уровень узла в C#

> Заплатка к CT1. Читать `CTF0_README_fixes.md`. Высокий приоритет. Идёт после `CTF1`.
> Правила — `AGENTS.md`.

## Симптом

В режиме `NestedSet` (без `LevelColumn`) у всех узлов `Level = 0`. Отступ узла в разметке —
`Node.Level * IndentPx`, поэтому дерево рисуется плоским: дети и внуки без сдвига вправо.

## Корневая причина (проверено по коду)

`ClaySqlTreeDataSource.MapRow`:

```csharp
Level = _source.Mode == ClayTreeHierarchyMode.ParentKey
            ? (parent?.Level + 1) ?? 0
            : row.Level ?? 0,
```

В NestedSet уровень берётся из `row.Level`, а `row.Level` заполняется в `ClayTreeData.MapRow`
только из выходной колонки `[_level]`, которая в SELECT попадает лишь `if (LevelColumn is not
null)`. Колонки нет → `row.Level == null` → `Level = 0` у каждого узла.

При этом для `ParentKey` уровень **уже** считается в C# как `parent.Level + 1`. Ровно тот же
приём подходит и для NestedSet: корни грузятся с `parent == null` (уровень 0), каждый
следующий уровень — дети известного родителя, значит `parent.Level + 1`. Колонка уровня для
отображения не нужна.

## Решение

Считать уровень от родителя в **обоих** режимах, а `row.Level` использовать только как
уточнение, если колонка всё же задана (обратная совместимость с редким случаем «Level есть»).

Файл `src/Clayzor.Lib.Web.Controls/Components/Tree/DataSources/ClaySqlTreeDataSource.cs`,
метод `MapRow`. Было:

```csharp
Level = _source.Mode == ClayTreeHierarchyMode.ParentKey
            ? (parent?.Level + 1) ?? 0
            : row.Level ?? 0,
```

Стало:

```csharp
// Уровень считаем от родителя в обоих режимах: корни — 0, каждый следующий уровень — parent+1.
// row.Level используется, только если колонка уровня реально задана в схеме (обычно её нет).
Level = row.Level ?? ((parent?.Level + 1) ?? 0),
```

Порядок именно такой: если `LevelColumn` задан и пришёл — доверяем БД; если нет (штатный
случай) — считаем от родителя. Для `ParentKey`, где `row.Level` всегда `null`, поведение
не меняется — по-прежнему `parent + 1`.

## Не делай

- Не возвращай обязательность `LevelColumn`, не трогай `ClayTreeSchema.Validate`.
- Не убирай ветку `row.Level` — при заданной колонке она корректна и дешевле.
- Не меняй билдер SQL (CTF1) и `ClayTreeData` — уровень считается в UI-маппере, ближе всего
  к родителю; тащить `parent.Level` в слой данных не нужно.
- Не добавляй колонку `[_level]` в SELECT при отсутствующей схеме — данных для неё нет.

## Проверка

Отдельного unit-теста маппер не требует (bUnit в проекте нет, компонент не тестируется —
см. `CT1` §9). Проверка ручная, на `/tree-test`, режим «Вложенные множества», схема без
`LevelColumn` (после применённого `CTF1`):

- «Оборудование», «Программное обеспечение» — уровень 0, без отступа;
- их прямые дети — отступ на один `IndentPx`;
- внуки («Ноутбуки» под «Компьютерная техника») — отступ на два;
- «Ноутбук Dell Latitude» — на три;
- переключить на `ParentKey` → отступы идентичны (доказывает единообразие расчёта уровня);
- «Обновить» → отступы сохраняются.

`dotnet build` + `dotnet test` — зелёные (существующие тесты не затрагиваются).

> CTF1 чинит **состав** уровней, CTF2 — **отступ**. Порознь каждый оставляет заметный дефект,
> поэтому проверять итог имеет смысл после обоих.
