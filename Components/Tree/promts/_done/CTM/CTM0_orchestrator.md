# CTM0 — Оркестратор: изменение данных в дереве ClayTree

Пакет добавляет в компонент `ClayTreeView` изменение данных: drag-and-drop (переупорядочивание и
переподчинение узлов), контекстное меню узла (редактирование, добавление ребёнка, удаление,
кастомные операции), а также два UX-требования (tooltip для длинных названий; липкая панель
фильтра). Все изменения БД идут через сервис `IClayTreeMutations`, который реализует приложение.

## Как выполнять

Промты выполняются строго по порядку: **CTM1 → CTM9**. Один шаг промта = один файл.
Файлы внутри промта пронумерованы в порядке правки. После каждого промта: проект собирается
(`dotnet build`) без ошибок и предупреждений по затронутым файлам.

Агент **не импровизирует** сверх написанного. Если фрагмент кода в промте расходится с реальным
файлом (переименовали метод, изменилась сигнатура) — агент останавливается и сообщает
расхождение, а не «чинит на глаз».

## Согласованный контракт (зафиксировано с заказчиком)

Эти решения — не предположения агента, а согласованные требования. Агент их не меняет.

### Целевой объект записи
Все модифицирующие запросы идут в **тот же объект, что и `SelectSql` дерева** (таблица или
представление с triggers INSTEAD OF). Отдельной опции целевой таблицы нет.

### Модели иерархии
- **NestedSet**: `L`/`R`/`Level` пересчитывают **триггеры в БД**. Компонент никогда не считает
  `L`/`R` сам.
- **ParentKey**: иерархия по `ParentId`.
- **Переподчинение** (reparent) выполняется **одинаково** в обоих режимах — один `UPDATE Parent`.
- **Переупорядочивание** (reorder) осмысленно только в **NestedSet** (в ParentKey нет ключа
  порядка). В ParentKey drag «между нодами» на том же уровне трактуется как no-op (или запрещён —
  см. CTM8).

### DnD: как различать reorder и reparent
Позиция указателя внутри строки-цели:
- верхние ~25% и нижние ~25% высоты строки → вставка **между** узлами → **reorder** (если тот же
  родитель) либо **reparent** (если перенос к другому родителю на «между» его детей — трактуется
  как reparent к этому родителю, позиция роли не играет, т.к. reorder только внутри одного
  родителя);
- средние ~50% → «**на узел**» → **reparent** (сделать перетаскиваемый узел ребёнком цели).

### Reorder — эталонный SQL (фиксированный, внутри компонента через сервис)
Компонент определяет сиблинга, **после которого** встаёт узел, берёт его текущее `L` и выполняет:

```sql
UPDATE <тот же объект, что SelectSql> SET <LeftColumn> = @NewL WHERE <IdColumn> = @Id;
```

- `@NewL` — значение `L` сиблинга, после которого встаёт узел. Для позиции 0 (в начало уровня) —
  `L` текущего первого сиблинга. Триггер нормализует порядок сам.
- `@Parent` в `UPDATE` **не участвует**; передаётся в метод только для валидации на стороне C#
  (что дроп в пределах того же родителя). Подтверждено заказчиком.

### Reparent — эталонный SQL
```sql
UPDATE <тот же объект, что SelectSql> SET <ParentColumn> = @Parent WHERE <IdColumn> = @Id;
```

### Add child
INSERT в тот же объект с указанием `Parent`; `L`/`R` проставит триггер. Триггеры типа
INSTEAD OF **не возвращают Id** новой строки. Поэтому:
- `AddChildAsync` **ничего не возвращает** (Task, без Id);
- после добавления компонент **перезагружает уровень родителя** согласно текущему фильтру и
  размеру порции. Новая нода может оказаться не видна (не подгружена/не проходит фильтр) — это
  ожидаемое поведение, подтверждено заказчиком.

### Delete
```sql
DELETE FROM <тот же объект, что SelectSql> WHERE <IdColumn> = @Id;
```
Всегда с подтверждением: «Вы уверены, что хотите удалить [Название ноды]?».

### Скалярная функция пути
Имя функции задаётся в опциях. Функция всегда имеет два параметра:
`@Code int` (идентификатор ноды), `@PathType bit` (0 — от потомка к родителю, 1 — от родителя к
потомку). Направление задаётся опцией-enum (по умолчанию 1 = ParentToChild). Вызов:
`SELECT <NodePathFunction>(@Code, @PathType)`.
В диалоге **редактирования** путь строится для **самой ноды**; в диалоге **добавления** —
для **родителя** (новой ноды ещё нет в БД).

### Запрет недопустимого дропа
Нельзя сделать узел ребёнком собственного потомка. Проверка:
- **NestedSet** — быстро в памяти по `L`/`R` (`target.Left > dragged.Left && target.Right < dragged.Right` → target внутри поддерева dragged → запрет);
- **ParentKey** — через БД: `IClayTreeMutations.IsDescendantAsync(targetId, draggedId)`.
Недопустимая цель подсвечивается визуально (запрещающий стиль), дроп на неё игнорируется.

### Обновление после изменений
Перезагрузить **только уровни затронутых родителей**, сохранив раскрытость и фокус остальных:
- reorder → уровень одного родителя;
- reparent → уровни **старого и нового** родителя;
- add → уровень родителя;
- delete → уровень родителя удалённой ноды;
- edit → **только текст самой ноды** (перечитать её строку и пересобрать `TextColumn`), уровень не
  трогаем.
Фокус (выделение) остаётся на выделенной ноде, если она не была удалена.

### Опциональность
Отдельные флаги в `ClayTreeOptions` (по умолчанию все `false`):
`EnableDragDrop`, `EnableEdit`, `EnableAddChild`, `EnableDelete`.
Контекстное меню рендерится, только если включён хотя бы один из edit/add/delete **или** задан
непустой список кастомных операций.

### Кастомные операции меню
Список в опциях: пункт = `{ Label, Icon?, OnExecute: Func<ClayTreeNode, Task> }`.

### Липкая панель фильтра
Фильтр и дерево — **в разных контейнерах**. Скролл только у контейнера дерева; панель фильтра над
ним не прокручивается.

### Tooltip
Если текст узла обрезан по ширине (`scrollWidth > clientWidth`) — при наведении показывать tooltip
с полным названием.

## Общие правила именования

- Новые partial-файлы компонента — в `Clayzor.Lib.Web.Controls/Components/Tree/`.
- Интерфейс и enum мутаций — там же (или в подпапке `Mutations/`, если так принято в проекте;
  проверить существующую структуру и следовать ей).
- Все пользовательские строки — на русском (как во всём компоненте).
- Ничего не логировать в UI; ошибки БД уже обрабатываются `DbManager`/`ClayErrorService`.

## Критерий готовности пакета

Все сценарии из CTM9 проходят вручную; проект собирается; существующие тесты дерева зелёные.
