# CTFR2 --- Сохранение глубокой раскрытости при `ReloadLevelAsync(null)`

## Контекст

Репозиторий: `Postnn/Clayzor.Lib.Web.Controls`.

Компонент: `Components/Tree/ClayTreeView`.

После CTMF2 ветка `ReloadLevelAsync(parent != null)` корректно сохраняет
глубокую раскрытость поддерева через сбор Id раскрытых потомков и
рекурсивное восстановление после reload.

Однако корневая ветка `ReloadLevelAsync(null)` использует другой
алгоритм:

-   сохраняет `_expanded`;
-   вызывает `LoadRootsAsync()`;
-   затем перебирает сохранённые Id и пытается найти их в `_byId`.

Проблема: `LoadRootsAsync()` очищает `_roots`, `_byId`, `_expanded` и
вызывает обычное `RestoreStateAsync()`. Архитектура persisted state
`ClayTree` восстанавливает только один путь до selected/anchor node, а
не все ранее раскрытые ветки.

Поэтому после root reload глубокие узлы из других раскрытых веток ещё
отсутствуют в `_byId`, и простой перебор сохранённых Id не способен
восстановить их.

Дефект проявляется прежде всего после:

-   reorder корневых узлов;
-   reparent узла из root;
-   reparent узла в root;
-   любых mutation flows, которые вызывают `ReloadLevelAsync(null)`.

## Задача

Сделать root reload симметричным по сохранению UI-state с non-root
reload: все ранее раскрытые ветки, которые по-прежнему существуют после
мутации, должны восстанавливаться сверху вниз.

## Требования

1.  Изучи актуальные:

    -   `Components/Tree/ClayTreeView.Mutations.cs`;
    -   `Components/Tree/ClayTreeView.Loading.cs`;
    -   `Components/Tree/ClayTreeView.State.cs` или актуальный partial с
        `RestoreStateAsync`;
    -   `Components/Tree/ClayTreeDragDrop.cs`;
    -   `Components/Tree/Models/ClayTreeNode.cs`;
    -   тесты reload/state/DnD.

2.  Сохрани архитектурное решение TF_I: persisted state дерева
    по-прежнему хранит один anchor/selected path. Не превращай
    `ClayTreeState` в persistent storage всех раскрытых веток.

3.  Исправление относится к краткоживущему in-memory state
    непосредственно вокруг mutation reload.

4.  Перед root reload собери snapshot раскрытости так, чтобы после
    уничтожения старых экземпляров nodes можно было восстановить
    раскрытые ветки.

5.  Восстановление должно идти сверху вниз:

    -   найти актуальный root;
    -   если он должен быть раскрыт --- раскрыть/загрузить его;
    -   после загрузки детей восстановить раскрытых детей;
    -   продолжить рекурсивно.

6.  Не рассчитывай на то, что глубокий node уже находится в `_byId`
    сразу после `LoadRootsAsync()`.

7.  Узел, удалённый или перемещённый так, что старый путь больше не
    существует, не должен вызывать исключение. Восстанавливай только
    реально существующие nodes.

8.  Не создавай duplicate nodes в `_byId` и не нарушай `Parent`,
    `IsLoaded`, `LoadedAllChildren`, `LastChildCursor`.

9.  Учитывай level paging: если раскрытый descendant не попал в первую
    страницу детей из-за пагинации, не делай бесконечную догрузку всего
    дерева без явной необходимости. Сначала проанализируй текущие
    гарантии порядка и mutation reload. Если для полного восстановления
    раскрытого пути требуется специальный поиск/догрузка, реализуй
    минимально безопасный вариант и зафиксируй решение.

10. Не вызывай `SaveStateAsync()` для каждого технически
    восстановленного раскрытия. Это не пользовательские expand actions.

11. Не вызывай внешние `OnNodeExpanded` callbacks для технического
    восстановления, если текущая архитектура восстановления их не
    вызывает.

## Важный сценарий

До root reorder:

``` text
A expanded
 └─ A1 expanded
     └─ A2

B expanded
 └─ B1 expanded
     └─ B2
```

После reorder `A`/`B` обе существовавшие раскрытые ветки должны остаться
раскрытыми:

``` text
B expanded
 └─ B1 expanded
     └─ B2

A expanded
 └─ A1 expanded
     └─ A2
```

Обычный persisted anchor может указывать только на одну из них --- это
не должно приводить к схлопыванию второй ветки во время mutation reload.

## Тесты

Добавь regression-тесты минимум для:

-   две одновременно раскрытые root-ветки с раскрытыми потомками
    глубиной \>= 2;
-   root reorder сохраняет обе ветки;
-   reparent из root сохраняет раскрытость unaffected root-веток;
-   reparent в root сохраняет раскрытость unaffected root-веток;
-   удалённый раскрытый узел спокойно отсутствует после reload;
-   `_expanded` после восстановления соответствует фактически раскрытым
    узлам;
-   восстановление не генерирует лишние persisted-state
    записи/callbacks, если это можно проверить текущими тестами.

Отдельно проверь взаимодействие с `RestoreStateAsync()`: root mutation
reload не должен зависеть от того, какой именно единственный anchor был
восстановлен persistent state.

## Ограничения

-   Не меняй модель persistent state TF_I.
-   Не переписывай весь loading pipeline.
-   Не меняй DnD SQL/mutation semantics.
-   Не делай массовый рефакторинг.
-   Не скрывай исключения reload/state.

## Документация

Зафиксируй в `Components/Tree/AGENTS.md` инвариант:

-   persistent restore восстанавливает один путь;
-   mutation-level reload временно сохраняет все раскрытые in-memory
    ветки затронутого уровня/дерева.
