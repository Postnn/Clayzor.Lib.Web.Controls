# TF_G — дефолтный фильтр (WHERE в ленивом режиме) и query-параметры

Два не-визуальных механизма установки фильтра: значения по умолчанию из опций и параметры
строки запроса. Ключевое отличие дефолтного фильтра — он **не** включает режим фильтра из TF_E
(предки/пометки/счётчик), а тихо подставляется как `WHERE` в обычную ленивую загрузку.

## Модель (из оркестратора)

- **Дефолтный фильтр** = условия из `ClayTreeOptions.FilterDefaults` (SqlName → значение).
  Тихое ограничение: WHERE в ленивом запросе уровня, ленивость/шевроны как обычно, пометок
  нет, строки «Найдено записей» нет (правило 7).
- Пользователь может **изменить** дефолтное значение (через диалог) → как только состав условий
  отличается от дефолтного, включается полный режим фильтра (TF_E).
- Признак — флаг `IsDefault` на условии. **Все** активные условия `IsDefault` → дефолтный
  режим; есть хоть одно не-`IsDefault` → пользовательский режим (TF_E).
- **Query-параметры** (правило 11): фильтр можно установить строкой запроса; сопоставление
  «имя параметра → колонка» из `ClayTreeOptions.FilterQueryParamMap`.

## 1. Флаг «дефолтности» условия

Проверить, есть ли на `ColumnFilter` подходящий признак (у грида URL-парсер различает
default/forced). Если нет — **не добавлять поле в общий `ColumnFilter`** (это тип фильтра,
общий с гридом; менять его — за рамками TF). Вместо этого дерево помечает дефолтные условия
на своей стороне: хранить отдельно набор SqlName дефолтных колонок (`_defaultFilterColumns`) и
считать «только дефолтный», если все листья `_filterRoot` — по колонкам из этого набора и не
трогались пользователем. Признак «не трогались» — сравнение значения с `FilterDefaults`.

Согласовать выбор в отчёте: флаг на `ColumnFilter` (если он там уже есть от грида) либо внешний
набор дефолтных колонок в дереве. Предпочтение — внешний набор, чтобы не трогать общий тип.

## 2. Дефолтный фильтр как WHERE

- при инициализации, если `FilterDefaults` непуст → построить `_filterRoot` из дефолтных
  условий (лист `ColumnFilter` на каждую пару SqlName→значение, оператор по умолчанию для типа),
  пометить их дефолтными;
- в **ленивом** пути загрузки (`BuildLevelSql` через `ClayTreeData`): если активен дефолтный
  фильтр → добавить его WHERE-фрагмент (через `ClayCompositeSqlBuilder.Build`) к условию уровня
  (`AND (<default-where>)`). Работает и для корней, и для детей;
- пометки/счётчик/предки — **не** включать; `MarksVisible=false` (TF_F);
- визуально дерево выглядит как обычное, просто данных меньше.

Точка вклинивания: `BuildLevelSql` уже строит `WHERE` уровня — дописать в неё дополнительный
предикат. Условие и параметры собираются в Controls (`ClayCompositeSqlBuilder`) и передаются в
Entities строкой+`dp`, как в TF_E. **Один** механизм передачи доп-WHERE на оба случая (дефолт
сейчас, возможно другое потом) — не плодить пути.

## 3. Переключение дефолт → пользовательский

- в `ApplyFilterAsync` (TF_E) уточнить проверку режима: **пользовательский**, если в
  `_filterRoot` есть хоть одно условие, которое не является нетронутым дефолтом; иначе —
  **дефолтный** (ленивый WHERE);
- пользователь открыл диалог, изменил дефолтное значение или добавил условие → часть условий
  перестала быть дефолтной → режим фильтра (TF_E) со всеми предками и пометками;
- пользователь удалил все свои условия, остались только дефолтные → назад в дефолтный режим.

## 4. Query-параметры

- при загрузке (после инициализации): прочитать query-строку, по `FilterQueryParamMap`
  (имя параметра → SqlName) собрать условия. Тип значения — по типу колонки (из TF_C);
- **приоритет с сохранённым состоянием** — как у грида: разобрать соглашение forced/default
  (грид: ключ без `_` — forced, применяется всегда; с `_` — default, только если нет
  сохранённого параметра). Переиспользовать `ClayGridUrlFilterParser`, если он не завязан на
  грид (проверить по TF_A); иначе — минимальный аналог для дерева, тем же соглашением;
- query-фильтр устанавливается как **пользовательский** (включает режим TF_E), если это не
  дефолт-ключ. Согласовать: forced из URL → пользовательский режим с пометками.

## Ловушки

- **Не менять общий `ColumnFilter`/`ClayFilterGroupNode`** ради дефолт-флага — дерево держит
  дефолтность на своей стороне (п.1). Иначе заденем грид.
- **Дефолтный WHERE и ленивый уровень.** Добавляя `AND (<default>)` в `BuildLevelSql`, следить,
  чтобы предикат применялся и к корневому уровню, и к детям, и не ломал NestedSet-предикаты
  (`L/R/level`). Обернуть дефолт в скобки.
- **«Только дефолтный» при пустом `FilterDefaults`.** Нет дефолтов и нет пользовательского
  фильтра → обычный режим, никаких WHERE. Не путать «нет фильтра» с «дефолтный фильтр».
- **Query + сохранённое состояние + дефолт** — три источника. Порядок разрешения зафиксировать
  явно (обычно: forced URL > сохранённое > default URL > FilterDefaults). Отметить в отчёте.

## Не делай

- Не трогай общий фильтр-тип и грид.
- Не показывай пометки/счётчик в дефолтном режиме (правило 7).
- Не дублируй разбор дерева фильтра — `ClayCompositeSqlBuilder`.
- Не выполняй SQL в Controls.
- Состояние/выделение (`LastExpandedId`/`SelectedIds`, сохранение по CLID) — **не здесь**, это
  TF_I. Здесь только фильтр из опций и URL.
