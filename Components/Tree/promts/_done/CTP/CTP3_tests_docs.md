## 1. Тесты (добрать, чего нет после CTP1)

Проверить, что покрыто CTP1; добавить недостающее. Только чистая логика, без БД/рендера.

`ClayTreeSqlBuilderTests`:
- первая порция (PageSize задан, Cursor=null): `TOP (@pageSize + 1)`, `ORDER BY [L]`, без
  `[L] > @cursor`;
- следующая порция (PageSize + Cursor): и `TOP`, и `[L] > @cursor`;
- без пагинации (PageSize=null): как прежде, без `TOP`/`@cursor` — существующие тесты живы;
- ParentKey + PageSize: игнор, без `TOP`/`@cursor`;
- корневой уровень + PageSize: без `TOP`/`@cursor` (корни не пагинируются);
- `TOP` именно `(@pageSize + 1)` со скобками; курсор — `@cursor`, не литерал; идентификаторы в
  `[]`; нет `OFFSET`/`ROW_NUMBER`.

`ClayTreeOptionsTests`: защёлка — `LevelPageSize == 0`, `LevelPagingMode == Button`.

Логику «HasMore/NextCursor» (отбрасывание n+1-й строки) вынести в CTP1 в **чистый** метод, если
она там встроена в загрузку и не тестируется, — тогда покрыть:
- пришло `n+1` строк → `HasMore=true`, вернулось `n`, `NextCursor` = `L` n-й;
- пришло `≤ n` → `HasMore=false`.
Если вынести нельзя без ломки — отметить в отчёте, тест не требовать (bUnit нет).

## 2. `AGENTS.md`

В разделе `ClayTreeView` добавить подраздел «Пагинация уровня»:
- кейсет по `L`, только NestedSet; ParentKey и корневой уровень не пагинируются;
- `LevelPageSize` (0 — выключено) и `LevelPagingMode` (Button/Scroll) — в `ClayTreeOptions`;
- курсор — одно значение `L`; `TOP(@n+1)` определяет «есть ещё»; догрузка **дописывает** в
  `Children` (`LoadedAllChildren`, `LastChildCursor`);
- не `OFFSET/FETCH`, не `ROW_NUMBER` (SQL Server 2008 R2);
- **условие валидности курсора:** пока порядок отображения = порядку `L`. Будущая алфавитная
  сортировка перестраивает `L` физически → курсор остаётся `L`; логическая сортировка без
  перестройки `L` потребует пересмотра;
- Scroll использует `IntersectionObserver` (JS-интероп), ссылки чистятся в `Dispose`.

## 3. След для серии TF (обязательно)

В `AGENTS.md`, там же, короткий абзац-стык (чтобы автор TF не проглядел):

> **Стык с фильтром (TF).** Пагинация уровня живёт в ленивой загрузке
> (`EnsureChildrenLoadedAsync` / `LoadMoreChildrenAsync`). Фильтр-режим строит набор целиком в
> пределах `MaxFilterRecords` и пагинацию уровня не использует. Единственный стык — ленивый
> разворот отфильтрованной ноды (TF_F): он идёт обычным ленивым путём и потому автоматически
> пагинируется. Специального кода не требует; при реализации TF_F — сослаться на это.

Если у тебя есть доступ к промтам серии TF (`Components/Tree/promts/TF_*` или в `_done`) и они
ещё не выполнены — **не редактировать их** (не твой шаг), только отметить в отчёте, что в TF_E/
TF_F нужна строка про использование пагинированного ленивого пути. Правка самих TF-промтов —
их автору.
