# CTMF1 — исправить no-op при Drag-and-Drop reorder

## Цель

Исправить ошибку в вычислении reorder для `ClayTreeView`, когда пользователь перетаскивает узел в позицию, в которой он уже находится.

Проблема относится только к логике DnD/reorder.

## Изменяемый файл

Только:

`Components/Tree/ClayTreeDragDrop.cs`

Другие файлы не изменять.

---

## Текущая проблема

В `ComputeNewLeft(...)` есть логика:

```csharp
if (ReferenceEquals(afterSibling, dragged))
    return target.Left ?? 0L;
```

Она некорректна для no-op сценария.

Пример:

```text
A
B
C
```

Пользователь перетаскивает `B` в зону `before` узла `C`.

Фактически дерево уже находится в требуемом состоянии:

```text
A
B
C
```

Никакой SQL reorder выполняться не должен.

Сейчас алгоритм определяет:

```text
target = C
afterSibling = B
afterSibling == dragged
```

после чего возвращает `C.Left` и вызывает:

```csharp
Mutations.ReorderAsync(...)
```

Это может привести к реальному изменению порядка вместо no-op.

---

## Требуемое поведение

Перед выполнением `ReorderAsync` определить ситуации, когда требуемое положение узла уже совпадает с текущим.

Такие операции должны завершаться без:

- диалога подтверждения;
- вызова `Mutations.ReorderAsync`;
- перезагрузки уровня;
- изменения выделения.

Минимально должны корректно определяться следующие случаи.

### Случай 1

Исходно:

```text
A
B
C
```

Перетаскиваем:

```text
B before C
```

Результат — no-op.

### Случай 2

Исходно:

```text
A
B
C
```

Перетаскиваем:

```text
B after A
```

Результат — no-op.

### Случай 3

Исходно:

```text
A
B
C
```

Перетаскиваем:

```text
A before B
```

Результат — no-op.

### Случай 4

Исходно:

```text
A
B
C
```

Перетаскиваем:

```text
C after B
```

Результат — no-op.

При этом реальные перемещения должны продолжить работать:

```text
C before A
A after C
B before A
B after C
```

---

## Требование к реализации

Не пытаться представлять no-op специальным значением `NewL`.

No-op должен определяться **до вызова `DoReorderAsync` либо в самом начале `DoReorderAsync` до ConfirmAsync**.

Предпочтительно добавить небольшой приватный helper с понятным именем, например:

```csharp
private static bool IsReorderNoOp(
    IReadOnlyList<ClayTreeNode> siblings,
    ClayTreeNode dragged,
    ClayTreeNode target,
    string zone)
```

Точная сигнатура может отличаться, если это лучше соответствует существующему коду.

Логика должна определяться по текущим индексам `dragged` и `target` в одном списке `siblings`.

Не сравнивать узлы по `Text`.

Использовать существующую объектную идентичность либо `Id` в соответствии с текущей архитектурой.

---

## `ComputeNewLeft`

После появления явной проверки no-op специальная ветка:

```csharp
if (ReferenceEquals(afterSibling, dragged))
    return target.Left ?? 0L;
```

не должна использоваться как способ обработки no-op.

Если после новой проверки эта ветка становится недостижимой и больше не нужна — удалить её.

Не менять согласованный контракт `NewL`:

- при вставке после sibling используется `L` этого sibling;
- для вставки в начало используется `L` текущего первого sibling;
- компонент самостоятельно `L/R` не пересчитывает;
- нормализацию выполняет SQL-trigger.

---

## Не менять

Не изменять:

- `IClayTreeMutations`;
- `ClaySqlTreeMutations`;
- SQL reorder;
- механику `before/on/after`;
- reparent;


# CTMF2 — сохранить глубокую раскрытость при ReloadLevelAsync

## Цель

Исправить восстановление состояния дерева после локальной перезагрузки уровня.

После `ReloadLevelAsync(parent)` должны сохраняться раскрытые потомки **на любой глубине**, если соответствующие узлы после перезагрузки всё ещё существуют.

## Изменяемый файл

Только:

`Components/Tree/ClayTreeView.Mutations.cs`

Другие файлы не изменять.

---

## Текущая проблема

Сейчас в `ReloadLevelAsync(ClayTreeNode? parent)` перед перезагрузкой запоминаются только непосредственно раскрытые дети:

```csharp
var previouslyExpanded = new HashSet<string>();
var childrenBefore = parent?.Children ?? _roots;

foreach (var ch in childrenBefore)
    if (ch.IsExpanded)
        previouslyExpanded.Add(ch.Id);
```

После reload тоже восстанавливается только этот уровень.

Пример:

```text
Parent
 └─ A              expanded
     └─ B          expanded
         └─ C
```

После:

```csharp
await ReloadLevelAsync(Parent);
```

узел `A` снова раскрывается, но новый экземпляр `B` уже остаётся закрытым.

Это нарушает требование CTM:

> при локальной перезагрузке затронутого уровня сохранить раскрытость остальных ранее раскрытых узлов.

---

## Требуемое поведение

Перед уничтожением старого поддерева сохранить идентификаторы всех раскрытых узлов внутри перезагружаемой ветки.

После загрузки нового уровня восстановить раскрытость рекурсивно.

Для примера:

```text
Parent
 └─ A              expanded
     └─ B          expanded
         └─ C
```

после `ReloadLevelAsync(Parent)` должно снова получиться:

```text
Parent
 └─ A              expanded
     └─ B          expanded
         └─ C
```

при условии, что `A` и `B` всё ещё существуют и имеют детей.

---

## Требование к реализации

Для `parent != null`:

1. До `RemoveFromIndex(...)` собрать `Id` всех раскрытых узлов во всём текущем поддереве детей `parent`.

2. Перезагрузить непосредственных детей `parent` существующим способом.

3. После загрузки пройти по новым объектам и рекурсивно восстановить состояние.

Логика восстановления для каждого узла:

```text
если Id отсутствует в сохранённом наборе:
    ничего не делать

если Id есть в наборе, но node.HasChildren == false:
    не раскрывать

если Id есть в наборе и node.HasChildren == true:
    node.IsExpanded = true
    добавить Id в _expanded
    EnsureChildrenLoadedAsync(node)
    после загрузки рекурсивно восстановить его детей
```

Можно добавить приватные helper-методы в этом же файле, например:

```csharp
private static void CollectExpandedIds(...)
private async Task RestoreExpandedDescendantsAsync(...)
```

Названия могут отличаться, но назначение должно быть очевидным.

---

## Важные ограничения

Не сохранять ссылки на старые `ClayTreeNode` как источник состояния.

После reload старые экземпляры уничтожаются и заменяются новыми.

Состояние между старым и новым деревом сопоставлять только через стабильный `Id`.

Не пытаться вручную переносить:

- `Children`;
- `Parent`;
- `Left`;
- `Right`;
- `RawId`;
- другие данные старого объекта.

Все данные нового объекта должны приходить из datasource.

---

## Корневой reload

Существующая отдельная логика для:

```csharp
parent == null
```

уже использует `_expanded`.

Не переписывать её без необходимости.

Если для устранения дублирования нужен маленький общий helper восстановления — допустимо.

Но задача этого промта — прежде всего исправить глубокое восстановление для `parent != null`.

---

## `_expanded`

После восстановления `_expanded` должен соответствовать реально раскрытым объектам нового дерева.

Не добавлять в `_expanded` узлы, которые:

- больше не существуют;
- больше не имеют детей;
- не были раскрыты до reload.

---

## Не менять

Не изменять:

- DnD;
- SQL;
- операции edit/add/delete;
- обработку исключений;
- `ClayTreeView.Loading.cs`;
- datasource;
- state store;
- другие файлы.

---

Проверить минимум:

```text

```

### Несколько уровней

```text

 └─ A expanded
     └─ B expanded
         └─ C
```

После reload `A` и `B` остаются раскрыты.

### Удалённый узел

Если `B` исчез из БД:

```text

 └─ A expanded
```

Восстановление не падает и не оставляет `B` в `_expanded`.

### Узел потерял детей

Если раньше узел был раскрыт, но после reload:

```csharp

```

он не должен помечаться раскрытым.

# CTMF3 — исключить использование stale newParent после reparent

## Цель

Исправить reparent, при котором после перезагрузки старого уровня код может продолжить работу со старым экземпляром `ClayTreeNode`, уже удалённым из актуального дерева.

## Изменяемый файл

Только:

`Components/Tree/ClayTreeDragDrop.cs`

Другие файлы не изменять.

---

## Текущая проблема

Сейчас `DoReparentAsync` сохраняет ссылки:

```csharp
var oldParent = dragged.Parent;
```

и получает `newParent` параметром.

После SQL выполняется:

```csharp
await ReloadLevelAsync(oldParent);

if (!ReferenceEquals(oldParent, newParent))
    await ReloadLevelAsync(newParent);
```

Проблема возникает, когда `newParent` находится внутри уровня или поддерева, которое было уничтожено первой перезагрузкой.

`ReloadLevelAsync(oldParent)` удаляет старые узлы из `_byId` и создаёт новые экземпляры.

После этого локальная ссылка `newParent` может указывать на старый объект, которого больше нет в актуальном дереве.

Вызывать:

```csharp
ReloadLevelAsync(newParent)
```

для такого объекта нельзя.

---

## Требуемое поведение

До первой перезагрузки сохранить стабильные идентификаторы:

```text
oldParentId
newParentId
draggedId
```

где для корня родительский Id может быть `null`.

После:

```csharp
await ReloadLevelAsync(oldParent);
```

нельзя считать исходный объект `newParent` актуальным.

Если требуется перезагрузить новый родительский уровень:

- для `newParent == null` работать как с корнем;
- для ненулевого родителя повторно найти **актуальный новый экземпляр** узла по сохранённому `Id`;
- использовать уже существующий `FindNodeById(...)`.

---

## Важный момент

Нужно различать:

1. старый и новый родитель логически одинаковы;
2. старый и новый родитель — разные объекты;
3. один из родителей — корень (`null`).

Для определения того, нужно ли reload второго уровня, не использовать только:

```csharp
ReferenceEquals(oldParent, newParent)
```

потому что после перезагрузки объектная ссылка не является стабильной идентичностью узла.

До reload определить логическую идентичность старого и нового родителя по стабильному `Id`.

Например:

```text
oldParent == null && newParent == null
    -> один уровень

oldParent != null && newParent != null && oldParent.Id == newParent.Id
    -> один уровень

иначе
    -> два уровня
```

Точная реализация может отличаться.

---

## Особый сценарий

Если после перезагрузки старого уровня новый родитель по сохранённому `Id` не найден в памяти, нельзя вызывать `ReloadLevelAsync` на старом stale-объекте.

Нужно безопасно обработать ситуацию в рамках текущей архитектуры.

Не загружать произвольные дополнительные ветки из БД специально для этого промта.

Не создавать собственную альтернативную систему поиска.

Использовать существующий `FindNodeById`.

---

## После операции

После всех необходимых reload:

```csharp
RestoreFocus(dragged.Id);
```

должен работать уже по актуальному дереву.

Лучше использовать заранее сохранённый стабильный `dragged.Id`, а не полагаться на актуальность старого объекта после reload.

---

Не изменять:

- `ReloadLevelAsync`;
- `ComputeNewLeft`;
- no-op reorder;
- SQL;
- `IClayTreeMutations`;
- `ClaySqlTreeMutations`;
- обработку исключений;
- другие файлы.

# CTMF4 — не проглатывать произвольные исключения после мутаций

## Цель

Устранить слишком широкое подавление `Exception` в операциях изменения дерева.

SQL-ошибки, уже обработанные `ISqlErrorHandler`, могут не пробрасываться дальше согласно существующей архитектуре, но ошибки обновления состояния/UI нельзя молча интерпретировать как SQL-ошибки.

## Изменяемый файл

Только:

`Components/Tree/ClayTreeView.Mutations.cs`

Другие файлы не изменять.

---

## Текущая проблема

В `EditNodeAsync`, `AddChildAsync`, `DeleteNodeAsync`, `BuildPathAsync` используются конструкции вида:

```csharp
catch (Exception ex) when (
    ex is not JSDisconnectedException
    and not ObjectDisposedException
    and not InvalidOperationException)
{
    // ошибка уже сохранена ISqlErrorHandler внутри DbManager
}
```

Но внутри `try` находится не только вызов SQL.

Например:

```csharp
await RunBusyAsync("Добавление…", async () =>
{
    await Mutations.AddChildAsync(...);

    parent.HasChildren = true;
    ...
    await ReloadLevelAsync(parent);
});
```

Если `Mutations.AddChildAsync` успешно изменил БД, а затем упал `ReloadLevelAsync`, исключение будет проглочено с ошибочным комментарием:

```text
ошибка уже сохранена ISqlErrorHandler
```

Это неверно.

Проблемы могут возникнуть в:

- reload;
- datasource;
- восстановлении дерева;
- callback;
- рендере;
- другой логике после успешного SQL.

Такие ошибки нельзя автоматически считать обработанными `ISqlErrorHandler`.

---

## Требуемое поведение

Сузить область подавления исключений так, чтобы она относилась только к операции, для которой действительно гарантировано сохранение SQL-ошибки через `ISqlErrorHandler`.

Логика после успешной мутации должна выполняться вне blanket `catch (Exception)`.

Например концептуально:

```csharp
try
{
    await Mutations.SomeOperationAsync(...);
}
catch (Exception ex) when (/* только ожидаемые SQL-ошибки, если это реально можно определить */)
{
    return;
}

await Reload...
```

Но не копировать этот пример буквально, если тип SQL-исключения в проекте другой.

---

## Перед изменением

Посмотреть существующий контракт:

- `DbManager`;
- `ISqlErrorHandler`;
- поведение `ExecuteAsync`/`ExecuteScalarAsync`.

Определить, что происходит после SQL-ошибки:

1. `DbManager` сохраняет ошибку и повторно бросает exception;
2. либо `DbManager` сохраняет ошибку и возвращает управление;
3. либо используется конкретный тип exception.

Не делать предположений.

Если `DbManager` сам уже полностью обрабатывает SQL-ошибку и не бросает её дальше, дополнительные `catch (Exception)` вообще не нужны.

---

## Операции

Проверить отдельно:

```text
EditNodeAsync
AddChildAsync
DeleteNodeAsync
BuildPathAsync
```

Для каждой операции убрать или сузить blanket catch.

---

## `InvalidOperationException`

Не использовать `InvalidOperationException` как универсальный признак JS lifecycle.

Это общий .NET exception, который может означать реальную программную ошибку.

В этом файле JS непосредственно почти не выполняется.

Если `InvalidOperationException` может возникать в конкретном `DialogService`/lifecycle сценарии, обрабатывать её только в узком месте, где причина действительно известна.

Не скрывать любые `InvalidOperationException` всей операции.

---

## `JSDisconnectedException` / `ObjectDisposedException`

Не расширять обработку этих исключений.

Если они действительно нужны вокруг dialog/lifecycle — сохранить только там, где это обосновано текущим кодом.

---

## `BuildPathAsync`

Для ошибки получения пути допустимо сохранить UX:

```text
путь не удалось получить -> диалог может открыться без пути
```

но только если ошибка действительно относится к `Mutations.GetNodePathAsync`.

Ошибка, возникшая вне этого вызова, не должна молча подавляться.

---

## Важное ограничение

Не менять пользовательский UX успешных операций.

После успешного:

```text
UpdateNodeAsync
AddChildAsync
DeleteAsync
```

должны выполняться существующие:

```text
RefreshNodeTextAsync
ReloadLevelAsync
```

Не переносить их внутрь подавляющего catch.

## Проверка

После изменения выполнить:

```bash
dotnet build
```

Если есть тесты — выполнить.

Проверить логически следующие сценарии.

### SQL update падает

Ошибка должна пройти через существующий `ISqlErrorHandler`.

После неуспешного SQL:

```text
RefreshNodeTextAsync
ReloadLevelAsync
```

не должны выполняться как будто операция успешна.

### SQL успешен, reload падает

Ошибка `ReloadLevelAsync` не должна быть проглочена как «уже обработанная SQL-ошибка».

### SQL успешен, refresh текста падает

Ошибка не должна быть проглочена как SQL-ошибка.

### Ошибка GetNodePathAsync

Если существующий UX предполагает необязательный путь:

```text
диалог открывается без Path
```

это поведение можно сохранить.
